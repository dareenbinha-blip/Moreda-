# MOREDA ERP — Leather Manufacturing Management (Starter v1.0)

A GitHub- and Render-ready custom web app for Moreda Leatherware. Responsive black-and-white interface, Python/FastAPI API, SQLAlchemy data models, session logins, role-based permissions, employee production tracking, quality control, and PostgreSQL deployment via `render.yaml`.

> **Status:** Tested starter application for evaluation. **Not a fully audited production ERP, accounting system, or payroll system.** For real company use, add data migrations, automated offsite backups, password-reset flow, monitoring, end-to-end security review, proper change/edit/correction workflows and compliance integrations. The free Render PostgreSQL database expires after 30 days; use a paid database with backups before recording important business data.

## Features already coded

| Module | Implemented functionality |
| --- | --- |
| Login & roles | Administrator first-run setup; signed sessions; password hashing; CSRF checks; server-side role restrictions |
| Staff | Administrator can register staff with individual passwords and one of six access roles |
| Customers & products | Customer directory, products and unit prices |
| Sales | Single-product orders, due dates, values and order statuses |
| Inventory | Material register, quantities, minimum levels, receipts/usage, movement history, nonnegative stock rule |
| Production | Jobs linked to sales orders, task assignments, manufacturing stage, targets, employee progress logs |
| Employee progress | Individual completion %, good/rejected quantities, timestamped progress history, team overview |
| Quality control | Inspect finished work, track passes/fails; packaging and tasks must be finished before QC approval |
| Dispatch safeguard | Order cannot move to dispatched unless associated job has QC approval |
| Reports | Management cards, team production progress, recent activity audit trail |

**First version limits:** One product per order; one job per order; no product BOM, multi-material allocations, quotations, invoicing, payment integration, purchasing, salary calculation, attendance, detailed rework authorization, tax/fiscalisation, exports, or full field editing yet. Employee production metrics are cumulative over all assigned jobs and should not be equated to individual effort or competency without context.

## A. Run the system on your own computer first

### 1. Install Python and unzip the project

- Install **Python 3.12 or newer** (https://www.python.org/downloads/). On Windows, choose the option to **Add Python to PATH** during installation.
- Extract `moreda_erp_github_ready.zip`, then open the folder containing `main.py`.
- In Windows File Explorer, click the address bar, type `cmd`, and press Enter to open a terminal in that folder (or use PowerShell / macOS Terminal).

### 2. Create a private `.env` file

Duplicate the `.env.example` file and rename the duplicate to `.env`.

Windows command prompt:

```bat
copy .env.example .env
```

macOS / Linux:

```bash
cp .env.example .env
```

Edit `.env` in a text editor. Replace `ADMIN_EMAIL`, `ADMIN_PASSWORD` and `SECRET_KEY` with values **you create privately**. The password must contain at least 12 characters and must not start with `CHANGE_ME`. Use a long random `SECRET_KEY` (at least 32 characters), for example one generated by a password manager. Leave `APP_ENV=development` and the SQLite `DATABASE_URL` as supplied.

**Never upload `.env`, secrets, or an actual business database to GitHub.** The supplied `.gitignore` excludes `.env` and `*.db`.

### 3. Install packages

```bash
python -m venv .venv
```

Activate the virtual environment:

Windows Command Prompt:

```bat
.venv\Scripts\activate.bat
```

macOS / Linux:

```bash
source .venv/bin/activate
```

Then install:

```bash
pip install -r requirements.txt
```

### 4. Start the application

```bash
uvicorn main:app --reload
```

Open **http://127.0.0.1:8000** in your browser. Log in with the administrator email and password from your local `.env`. The application will create a local `moreda_local.db` database on first launch.

## C. Deploy GitHub repository to Render using the Blueprint

Render documentation: https://render.com/docs/infrastructure-as-code

1. Create/sign in to a Render account at **https://dashboard.render.com/**.
2. Connect your GitHub account to Render and allow access to the private `moreda-erp` repository.
3. In Render, open **Blueprints** and choose **New Blueprint Instance** (wording may vary).
4. Select the **`moreda-erp` GitHub repository**.
5. Render reads `render.yaml` and prepares **two resources**:
   - `moreda-erp` — Python web application.
   - `moreda-erp-db` — PostgreSQL database.
6. When prompted for required environment variables, provide:
   - `ADMIN_EMAIL` → the email address you want to use for your first administrator account.
   - `ADMIN_PASSWORD` → a **unique password of 12 or more characters**. Save it in a password manager; don't share it.
   - `SECRET_KEY` is generated automatically by Render.
   - `DATABASE_URL` is wired automatically from Render PostgreSQL — don't replace it with SQLite.
   - `APP_ENV=production` is supplied by the Blueprint (enables HTTPS-only session cookies).
7. Review the services/plans before clicking **Apply** or **Deploy**. The supplied plan is *free for a temporary prototype only*; Render may change plan availability or prompt you to select a plan.
8. Open the resulting `moreda-erp` web service. Under **Events/Logs**, wait for the deploy to succeed. If it fails, open the logs to read the specific error.
9. When the service is marked **Live**, open its HTTPS URL, typically `https://moreda-erp.onrender.com` (Render determines the exact URL). Sign in with `ADMIN_EMAIL` and `ADMIN_PASSWORD`.
10. Create employee users; register a sample customer/product/material; record one test order, job, task progress and QC inspection.

### Optional: configure a web service manually

If you do not use Blueprints, first create a **Render PostgreSQL** database. Then create a **Render Web Service** connected to the GitHub repo using these values:

| Render setting | Value |
| --- | --- |
| Runtime | Python 3 |
| Build command | `pip install -r requirements.txt` |
| Start command | `uvicorn main:app --host 0.0.0.0 --port $PORT` |
| Health check path | `/healthz` |
| `APP_ENV` | `production` |
| `DATABASE_URL` | PostgreSQL **internal** database connection URL from Render |
| `SECRET_KEY` | New random secret, 32+ characters |
| `ADMIN_EMAIL` | Your desired admin email |
| `ADMIN_PASSWORD` | New secure password (12+ characters) |

The Python version comes from `.python-version` (3.12).

## D. How to use the ERP

1. **Administrator:** Log in and open **Employees & users**. Create a separate login for each worker. Give production employees the `employee` role and quality inspectors the `quality` role.
2. **Sales:** Add a **Customer** and a **Product**, then create a **Sales order**. The default currency shown is USD; there is no multi-currency logic in v1.
3. **Inventory:** Create material records and record received leather using a stock `in` movement. When materials are consumed, record stock `out` against a job reference. Product BOM automatic deductions are not implemented yet.
4. **Supervisor:** Open **Production jobs**, create a job from a sales order, then assign tasks in **My production tasks** using stages such as Cutting, Stitching, Assembly, Finishing and Packaging.
5. **Production employee:** Sign in, open **My production tasks**, choose an assigned task, and record each batch of **good** and **rejected** units. Staff can update only their own tasks; supervisors can report on tasks across the team.
6. **Supervisor/Director:** Use **Staff performance** to see target, good units, rejected units and task progress. Also monitor **Overview** for live work in progress.
7. **Quality officer:** After all tasks are finished and packaging has reported the full job quantity, record a **Quality inspection**. The job becomes `qc_approved` once total passed units equal the planned quantity.
8. **Sales:** Change the order status to `dispatched` only once QC has approved the job.

### Employee progress policy

- Each progress entry is stored with its task, the **reporting user's ID**, quantities, note and timestamp.
- An employee can only update tasks assigned to them; supervisors/admins can report for staff (using their own reporting account, which the log records).
- `good_qty` counts successful units; `rejected_qty` counts unsuccessful attempts. Rejected units can be reworked and do not count toward good-unit completion.
- Task completion percent = `good_qty / target_qty × 100`.
- Employee performance page shows **cumulative** totals. Targets might count the same physical bag at multiple manufacturing stages, so **do not sum these as unique finished bags**.

## F. Troubleshooting

| Problem | What to check |
| --- | --- |
| `ADMIN_EMAIL and ADMIN_PASSWORD` error | Set both before first start; password must be 12+ characters and not start with `CHANGE_ME`. |
| `SECRET_KEY must be a strong random value` | Set a random 32+ character secret; Render Blueprint does this automatically. |
| `ModuleNotFoundError` | Install from `requirements.txt` and activate the virtual environment. |
| `connection refused` or Postgres auth issue | Check the `DATABASE_URL` PostgreSQL URL and whether the Render database is running. |
| `403 Invalid session security token` | Reload page and sign in again. Avoid multiple environments/versions with mismatched session secrets. |
| Login rejected | Use first-run admin values, not placeholder values in `.env.example`. If a database was created earlier, changing `ADMIN_PASSWORD` doesn't reset the account. |
| Render deployment fails | Check Render **Logs**. Confirm build/start commands, environment variables, and `.python-version`. |
| Data disappears after restart | Never use SQLite on Render's ephemeral web filesystem; connect to persistent PostgreSQL. |
| Free database expires | Upgrade to a supported paid PostgreSQL plan before its expiration and verify backups. |
